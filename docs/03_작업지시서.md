## 0. 사용 방법

세션을 시작할 때 아래처럼 지시한다.

```
docs/03_작업지시서.md의 T1.2를 진행해. 시작 전에 docs/01, docs/02의 관련 절을 읽고,
완료 기준의 검증 명령을 모두 통과시킨 뒤 진행 현황 표를 갱신해.
```

마일스톤 단위로 맡길 때는 이렇게 지시한다.

```
docs/03_작업지시서.md의 M1 작업을 T1.1부터 순서대로 진행해.
작업 하나가 끝날 때마다 검증 명령을 실행하고 커밋한 뒤 다음 작업으로 넘어가.
막히면 멈추고 무엇이 막혔는지 보고해.
```

## 1. 공통 규칙

### 작업 방식

- 작업을 시작하기 전에 해당 작업의 "참조"에 적힌 요구사항과 설계서 절을 읽어.
- 작업 순서를 지켜. 앞 작업의 완료 기준을 통과하지 못했으면 다음 작업으로 넘어가지 마.
- 완료 기준의 검증 명령을 직접 실행하고, 통과한 출력을 확인한 뒤에만 완료로 표시해.
- 작업 하나가 끝나면 커밋해. 커밋 메시지는 `T1.2: PKCS#11 세션과 키 생성`처럼 작업 번호로 시작해.
- 작업이 끝나면 이 문서 맨 아래 "진행 현황" 표의 상태와 날짜를 갱신해.
- 설계서와 다르게 구현해야 하면 먼저 멈추고 이유를 보고해. 승인받은 뒤 `docs/01`의 결정사항과 `docs/02`를 고치고 나서 구현해.
- 지시된 범위 밖의 기능을 추가하지 마. 필요해 보이면 제안만 해.

### 보안 규칙

- 개인키, 니모닉, HSM PIN, 래핑 키, 승인자 개인키, DB 비밀번호를 코드·로그·테스트 출력·커밋에 넣지 마.
- `deploy/certs/`, `deploy/secrets/`, 승인자 키 파일, SoftHSM2 토큰 디렉터리를 커밋하지 마. `.gitignore`에 먼저 넣어.
- 업무 서버(`cmd/apid`와 그것이 쓰는 패키지)에서 `internal/hsm`을 import하지 마. 빌드 검사로 막아.
- 서명 서버가 원장 노드에 접속하게 만들지 마.
- 테스트를 통과시키려고 검사 단계(설계서 5.3)를 건너뛰는 옵션이나 우회 경로를 만들지 마.
- 메인넷이나 외부 공개망에 접속하는 설정을 넣지 마. 로컬 네트워크만 써.

### 코드 규칙

- ORM을 쓰지 마. `database/sql`과 직접 작성한 SQL을 써.
- 금액과 수량에 `float`를 쓰지 마. `*big.Int`와 문자열을 써.
- 암호 알고리즘과 Shamir 분할을 직접 구현하지 마. 검증된 공개 라이브러리를 써.
- 오류를 삼키지 마. 감싸서 위로 올리고, 서명 거부는 설계서 5.3의 단계별 오류 코드로 구분해.
- 라이브러리와 도구 버전은 추측하지 말고 공식 문서나 저장소에서 확인한 뒤 고정해.
- Besu, SoftHSM2, PKCS#11 메커니즘처럼 동작이 불확실한 부분은 기억에 의존하지 말고 공식 문서를 확인하거나 실측 스크립트로 검증해.
- 주석과 문서는 한국어로 써. 식별자는 영어로 써.
- 문서의 용어는 업계에서 통용되는 일반 용어로 써. 특정 벤더의 제품 용어를 일반 용어처럼 쓰지 마.

### 테스트 규칙

- 기능을 만들면 단위 테스트를 같이 만들어. 거부 사례(설계서 16절)는 빠짐없이 테스트로 남겨.
- 통합 테스트는 실제 SoftHSM2, MySQL, Besu를 띄워서 실행해. HSM을 모의 객체로 바꿔서 통합 테스트를 통과시키지 마.
- 실패하는 테스트를 지우거나 건너뛰게 만들지 마. 원인을 고쳐.

## M0 골격과 기술 실측

### T0.1 저장소 초기화

- 목표: 빌드와 테스트가 도는 빈 골격을 만든다.
- 참조: 설계서 3절, 4절
- 작업
  - `git init`, `.gitignore`(비밀·생성물 포함), `go.mod`, 설계서 3절의 디렉터리 구조를 만들어.
  - `cmd/apid`, `cmd/signerd`, `cmd/stoctl`이 버전만 출력하도록 만들어.
  - `Makefile`에 `build`, `test`, `lint`, `up`, `down`, `it`, `demo` 타깃을 만들어. 아직 내용이 없는 타깃은 안내 문구만 출력하게 해.
  - `apid`가 `internal/hsm`을 import하면 실패하는 검사를 `make lint`에 넣어.
- 완료 기준: `make build && make test && make lint`가 성공한다.

### T0.2 Besu 로컬 네트워크

- 목표: QBFT 검증 노드 4개, 가스비 0인 허가형 네트워크를 띄운다.
- 참조: 설계서 10.1, 요구사항 B-5-2
- 작업
  - Besu 공식 문서에서 QBFT 네트워크 구성과 가스비 없는 네트워크 구성 절차를 확인해.
  - `deploy/besu/`에 genesis와 노드 설정을 만들고 `deploy/docker-compose.yml`에 노드 4개를 넣어.
  - RPC는 Compose 내부 네트워크에만 열고, 호스트에는 노드 하나만 `127.0.0.1`로 바인딩해.
  - `scripts/check-besu.sh`로 블록 생성, 검증 노드 수, 잔액 0인 계정의 트랜잭션 전송 성공을 확인해.
  - 확정한 트랜잭션 유형(레거시 또는 EIP-1559)과 가스비 0 구성 방식을 `docs/01`의 결정사항에 추가해.
- 완료 기준: `make up && scripts/check-besu.sh`가 성공하고, 노드 하나를 내려도 블록이 계속 생성된다.

### T0.3 SoftHSM2 실측: secp256k1 서명

- 목표: 가장 큰 기술 위험을 먼저 확인한다.
- 참조: 설계서 6.1, 6.2, 요구사항 7절
- 작업
  - `deploy/signerd/Dockerfile`에 SoftHSM2를 포함해. 토큰 디렉터리는 볼륨으로 분리해.
  - `scripts/probe-hsm/`에 Go 실측 프로그램을 만들어. 토큰 초기화 → secp256k1 키 생성(추출 불가) → `CKM_ECDSA` 서명 → low-s 정규화 → 복구 식별자 계산 → 주소 일치 확인까지 해.
  - 이 서명으로 만든 트랜잭션을 T0.2 네트워크에 보내 확정되는지 확인해.
  - 결과를 `docs/증빙/실측_HSM_서명.md`에 남겨(메커니즘 이름, 속성, 출력 형식, 성공 여부).
- 완료 기준: 실측 프로그램이 성공하고 트랜잭션이 확정된다. 실패하면 멈추고 대안(다른 소프트웨어 HSM, 클라우드 KMS)을 비교해 보고해.

### T0.4 SoftHSM2 실측: 키 래핑

- 목표: 루트 키 백업 방식을 확정한다.
- 참조: 설계서 6.3, 결정사항 D-3
- 작업
  - 실측 프로그램에 AES-256 래핑 키 주입, EC 개인키 `C_WrapKey`, 빈 토큰에 `C_UnwrapKey`, 복원된 키의 주소 일치 확인을 추가해.
  - 지원되는 래핑 메커니즘 이름을 기록해.
  - 지원되지 않으면 설계서 6.3의 대체 방식(토큰 저장소 암호화 사본)으로 바꾸고 `docs/01` 결정사항과 리스크, `docs/02` 6.3을 고쳐.
- 완료 기준: `docs/증빙/실측_HSM_래핑.md`에 결과가 있고, 설계서 6.3의 "실측 필요" 항목이 확정 내용으로 바뀌어 있다.

### T0.5 DB와 마이그레이션

- 목표: 스키마와 DB 계정을 분리한다.
- 참조: 설계서 12절, NFR-2
- 작업
  - Compose에 MySQL 8을 넣고 `api`, `signer` 스키마와 각각의 계정을 만들어.
  - 마이그레이션 도구를 하나 골라 `migrations/api`, `migrations/signer`에 설계서 12절의 테이블을 만들어.
  - 서버용 계정에는 `audit_log` 테이블에 `INSERT`, `SELECT`만 줘. 마이그레이션은 별도 계정으로 실행해.
  - `make migrate` 타깃을 만들어.
- 완료 기준: `make up && make migrate`가 성공하고, 서버용 계정으로 `audit_log`에 `UPDATE`·`DELETE`를 시도하면 실패하는 테스트가 통과한다.

## M1 서명 서버 (FR-1, FR-2)

### T1.1 mTLS와 서버 골격

- 참조: 설계서 13절, 15절, FR-1.3
- 작업
  - `scripts/gen-certs.sh`로 로컬 CA와 `apid`, `signerd`, `stoctl` 인증서를 만들어.
  - `internal/transport`에 mTLS 서버·클라이언트와 CN 허용 목록 검사를 만들어.
  - `signerd`, `apid`에 `/healthz`와 설정 로딩, 기동 점검(설계서 15절)을 만들어.
- 완료 기준: 인증서 없는 호출과 허용되지 않은 CN의 호출이 거부되는 테스트가 통과한다.

### T1.2 PKCS#11 세션과 키 생성

- 참조: 설계서 6.1, 6.4, FR-1.2, FR-2.1
- 작업
  - `internal/hsm`에 토큰 로그인, 세션 풀, 키 생성, 공개키 조회, 객체 삭제를 만들어.
  - PIN은 Docker secret 파일에서 읽어. 환경 변수로 받지 마.
  - `scripts/init-tokens.sh`로 설계서 2절 표의 토큰 네 개를 초기화해.
  - `internal/signer`에 `Signer` 인터페이스와 HSM 구현을 만들어.
- 완료 기준: 통합 테스트에서 토큰별 키 생성과 조회가 성공하고, 추출 불가 키의 값 읽기 시도가 실패한다.

### T1.3 EVM 서명 완성

- 참조: 설계서 6.2, FR-1.5
- 작업
  - `internal/signer`에 low-s 정규화와 복구 식별자 계산을 만들어.
  - `internal/evmtx`에 T0.2에서 확정한 유형의 트랜잭션 생성과 서명 결합을 만들어.
  - high-s가 나오는 경우를 포함한 단위 테스트를 만들어. go-ethereum의 서명 검증으로 대조해.
- 완료 기준: 단위 테스트가 통과하고, HSM 키로 서명한 트랜잭션이 Besu에서 확정되는 통합 테스트가 통과한다.

### T1.4 키 레지스트리와 기관별 분리

- 참조: 설계서 2절, 6.1, 12.1, FR-2
- 작업
  - `internal/keyreg`에 키 등록, `(원장, 기관, 용도)` 조회, 상태 변경을 만들어.
  - `signerd init --bootstrap`으로 토큰, 초기 키, 승인자, 정책을 한 번만 넣게 만들어. 두 번째 실행은 거부해.
  - 기동 점검에서 레지스트리의 ACTIVE 키가 HSM에 실제로 있는지 대조해.
- 완료 기준: 기관 A의 요청으로 기관 B의 키를 얻을 수 없는 테스트, 용도가 다른 키를 얻을 수 없는 테스트가 통과한다.

### T1.5 트랜잭션 해석과 서명 API 1차

- 참조: 설계서 5.2, 5.3, 10.3, FR-1.1, FR-1.4
- 작업
  - `internal/intent`에 intent 구조, 정규화, 해시를 만들어. 정규화 결과가 고정된 테스트 벡터를 만들어.
  - `internal/evmtx`에 미서명 tx 해석과 intent 대조(`VerifyTx`)를 만들어. 네트워크에 접근하지 않는 순수 함수로 만들어.
  - `POST /v1/sign/tx`를 만들어. 이 단계에서는 설계서 5.3의 1~4, 7~9단계를 구현하고, 5·6단계(정책, 승인)는 M2에서 채워. 그때까지 이 API는 테스트 전용 빌드 태그로만 열어.
- 완료 기준: intent와 다른 calldata, 다른 `to`, 0이 아닌 `value`, 다른 `chainId`가 각각 거부되는 테스트가 통과한다. M1 완료 기준인 "HSM 키로 서명한 트랜잭션이 Besu에서 확정"이 `make it`으로 확인된다.

## M2 승인과 감사 (FR-3, FR-4)

### T2.1 감사로그 해시 체인

- 참조: 설계서 8절, FR-4.1, FR-4.2
- 작업
  - `internal/audit`에 추가, 구간 검증, 머리 조회를 만들어. 추가는 머리 행을 잠근 DB 트랜잭션 안에서 해.
  - payload에 비밀 값이 들어가지 않도록 허용 필드만 기록하는 구조로 만들어.
  - M1에서 만든 서명·키 작업에 감사 기록을 붙여. 업무 기록과 감사 기록은 같은 DB 트랜잭션으로 저장해.
  - `stoctl audit verify`를 만들어.
- 완료 기준: 동시에 100건을 추가해도 체인이 끊기지 않는 테스트, 관리 계정으로 한 행을 고친 뒤 검증이 그 `seq`에서 실패하는 테스트가 통과한다.

### T2.2 승인자 키와 승인 서명

- 참조: 설계서 5.2, 7.1, FR-3.1, D-2
- 작업
  - `stoctl approver keygen`으로 암호로 보호한 Ed25519 키 파일을 만들어.
  - `internal/approval`에 승인 서명 생성과 검증을 만들어.
  - 서명 서버의 `approvers`, `approver_groups` 조회를 만들어.
- 완료 기준: 위조 서명, 다른 intent에 대한 서명 재사용, 비활성 승인자의 서명이 거부되는 단위 테스트가 통과한다.

### T2.3 정책 엔진

- 참조: 설계서 7.2, FR-3.2
- 작업
  - `internal/policy`에 정책 모델과 평가를 만들어. 평가 결과는 통과 또는 구체적인 거부 코드야.
  - 함수 허용, 수량 한도, 수신 계좌 화이트리스트, 필요 승인 수, 승인자 그룹, 가스 한도 상한을 검사해.
- 완료 기준: 정책 항목별 통과·거부 단위 테스트가 통과한다.

### T2.4 서명 API 완성

- 참조: 설계서 5.3
- 작업
  - `POST /v1/sign/tx`에 5·6단계를 채우고 테스트 전용 빌드 태그를 제거해.
  - `request_id` 멱등 처리를 만들어(D-6).
  - 모든 거부를 감사로그에 사유와 함께 남겨.
- 완료 기준: 설계서 16절의 거부 사례 중 서명 서버에 해당하는 항목이 모두 테스트로 있고 통과한다.

### T2.5 요청 상태 기계와 업무 API

- 참조: 설계서 5.4, 5.5, 13.2, FR-3.3, NFR-3, NFR-4
- 작업
  - `internal/workflow`에 상태 전이를 조건부 갱신으로 만들어.
  - `apid`에 기안, 승인·반려, 조회 API를 만들어. 기안 시 사전 정책 검사를 해서 명백한 위반은 일찍 돌려줘.
  - APPROVED 요청을 서명 서버로 보내는 작업자, 만료 처리 작업자를 만들어.
  - nonce 할당을 만들어.
  - `stoctl request draft|approve|reject|show|list`를 만들어.
- 완료 기준: 같은 요청을 두 작업자가 동시에 처리해도 서명 요청이 한 번만 나가는 테스트, 서명 서버를 내린 동안 요청이 APPROVED에 머물다가 다시 올리면 진행되는 통합 테스트가 통과한다.

### T2.6 동결과 알람

- 참조: 설계서 7.3, 7.4, FR-3.5, D-5
- 작업
  - `POST /v1/freezes`(보안관리자 1인 서명)와 해제(M-of-N)를 만들어.
  - `stoctl freeze key|institution|ledger`가 서명 서버를 직접 호출하게 만들어.
  - `internal/alarm`에 설계서 7.4의 규칙을 만들어.
- 완료 기준: 업무 서버를 내린 상태에서 동결이 성공하고, 동결된 키의 서명 요청이 거부되며, 1인 서명으로 해제를 시도하면 거부되는 테스트가 통과한다.

### T2.7 감사 체크포인트

- 참조: 설계서 8절, FR-4.3
- 작업
  - 서명 서버가 주기적으로 두 체인의 머리를 AUDIT 키로 서명해 DB와 체크포인트 파일에 쓰게 만들어.
  - `stoctl audit verify`가 체크포인트 서명도 확인하게 만들어.
- 완료 기준: 체크포인트 이후 구간을 통째로 지우고 다시 쓴 경우를 검증이 잡아내는 테스트가 통과한다.

## M3 원장 연계와 키 생애주기 (FR-5, FR-6)

### T3.1 토큰증권 컨트랙트

- 참조: 설계서 10.2, FR-6.2
- 작업
  - `contracts/`에 `SecurityToken`을 만들어. OpenZeppelin의 접근 제어와 일시 정지 구성 요소를 써.
  - 역할, 계좌 등록, 기관 일치 검사, 처분제한, 유통 상태를 설계서대로 만들어.
  - 일반 ERC-20의 `transfer`, `approve`를 제공하지 마.
  - Foundry 테스트로 역할별 허용·거부, 다른 기관 계좌의 대체 거부, 처분제한, 유통 정지를 검증해.
  - `abigen`으로 Go 바인딩을 만들고 `make gen`에 넣어.
- 완료 기준: `make test-contracts`가 성공한다.

### T3.2 Besu 어댑터

- 참조: 설계서 10.3, FR-6.1, FR-6.3
- 작업
  - `internal/ledger`에 인터페이스를, `internal/ledger/besu`에 구현을 만들어.
  - T1.5의 임시 tx 생성 코드를 `BuildTx`, `VerifyTx`로 옮겨.
  - 제출 재시도는 같은 서명된 tx를 다시 보내는 방식으로만 해. 이미 알려진 tx 응답은 성공으로 처리해.
- 완료 기준: 같은 서명된 tx를 두 번 제출해도 체인에 한 번만 반영되는 통합 테스트가 통과한다.

### T3.3 배포와 초기 권한 부여

- 참조: 설계서 2절, 10.2
- 작업
  - 종목 배포를 승인이 붙은 요청 유형으로 만들어. 배포 키는 플랫폼 CONTRACT_ADMIN 키야.
  - 배포 후 기관 키에 역할을 부여하는 요청들을 `scripts/bootstrap-security.sh`로 묶어.
  - 배포 트랜잭션도 서명 서버의 해석·대조를 거치게 해. 배포 바이트코드 해시를 intent에 넣어 대조해.
- 완료 기준: 스크립트 한 번으로 종목 하나가 배포되고 기관 A·B 키에 역할이 부여된다. 모든 단계가 감사로그에 남는다.

### T3.4 이벤트 수신과 전자등록정보 보존

- 참조: 설계서 10.4, FR-6.4
- 작업
  - `internal/registry`에 커서 기반 수신 작업자를 만들어. 이벤트 저장과 커서 갱신은 같은 DB 트랜잭션으로 해.
  - 요청의 CONFIRMED 전이를 영수증 기준으로 처리해.
- 완료 기준: 수신 작업자를 중간에 죽였다 살려도 이벤트가 빠지거나 중복되지 않는 통합 테스트가 통과한다. 발행 → 계좌 등록 → 계좌대체가 `stoctl`로 끝까지 수행된다.

### T3.5 키 교체와 폐기

- 참조: 설계서 9절, FR-5.1~FR-5.3, FR-3.4
- 작업
  - `POST /v1/key-ops`에 생성, 퇴역, 폐기를 만들어. 모두 보안관리자 M-of-N 승인이 필요해.
  - `stoctl key rotate`가 새 키 생성 → 역할 부여 → 이전 역할 회수 → 이전 키 퇴역을 순서대로 기안하게 만들어.
  - 폐기는 RETIRED 키에만 허용하고, 삭제 후 HSM에 객체가 없는지 확인해.
- 완료 기준: 교체 후 새 키로 발행이 성공하고 이전 키로는 서명 서버와 컨트랙트 양쪽에서 거부되는 통합 테스트가 통과한다. 폐기 증적이 감사로그에 있다.

### T3.6 백업과 복구 리허설

- 참조: 설계서 6.3, FR-5.4
- 작업
  - T0.4에서 확정한 방식으로 `stoctl key ceremony`, `stoctl key backup`, `stoctl key restore`를 만들어.
  - 래핑 키 조각은 보관자별 파일로 내보내고 화면에 출력하지 마.
  - `scripts/rehearsal-restore.sh`로 빈 토큰에 복구해 같은 주소와 서명 검증을 확인하고, 결과를 `docs/증빙/복구리허설_YYYYMMDD.md`에 남겨.
- 완료 기준: 리허설 스크립트가 성공하고 증빙 문서가 생성된다. 조각 1개로는 복구가 실패한다.

### T3.7 분실·도난 대응 시나리오

- 참조: 설계서 9절, FR-5.5, 요구사항 B-4-1
- 작업
  - `scripts/incident-key-compromise.sh`로 동결 → 역할 회수 → 유통 정지 → 새 키 투입 → 유통 재개 → 이전 키 폐기를 순서대로 실행해.
  - 각 단계의 소요 시간과 감사로그 `seq`를 출력해.
- 완료 기준: 스크립트가 끝까지 성공하고, 중간에 탈취된 키로 시도한 요청이 거부된 기록이 감사로그에 있다.
