## 1. 목적과 범위

업무 서버는 키를 갖지 않고, 분리된 서명 서버가 HSM 안의 키로 승인된 요청만 서명하는 구조를 허가형 분산원장 위에서 끝까지 동작시킨다. "디지털자산 지갑·키관리 시스템 개발" 직무의 키 관리 아키텍처와 분산원장 연계 계층을 코드와 문서로 증명하는 것이 목적이다.

| 구분 | 범위 |
|---|---|
| 필수 (P0) | 서명 서버 분리, HSM(PKCS#11) 키 금고, 원장·기관별 금고 분리, 승인 워크플로우, 감사로그, 키 생성·교체·폐기·백업·복구 |
| 필수 (P0) | 허가형 원장(Hyperledger Besu) 어댑터: 트랜잭션 생성·제출·이벤트 수신 |
| 권장 (P1) | 연계장부(모의 계좌·잔고 원장)와 온체인 잔고 대사 |
| 권장 (P1) | 키관리 정책 설명서, 가이드라인 요건 대응표 |
| 선택 (P2) | MPC(TSS) 서명기, Hyperledger Fabric 어댑터와 인증서(CA) 관리 |

제외 범위

- 실물 HSM, 상용 MPC·커스터디 솔루션 연동 (SoftHSM2와 오픈소스로 대체)
- 예탁결제원 토큰증권 플랫폼과의 실제 연계, 총량관리 노드 구현
- 투자자용 화면, 주문·매매 체결, 실명 확인
- 운영 환경 수준의 망 분리와 재해복구 센터 구축 (설계 문서로만 다룸)

## 2. 근거 규정: 예탁원 가이드라인

한국예탁결제원 「토큰증권 분산원장 표준요건 가이드라인」(2026년 9월, 금융위원회 「토큰증권 정책방향」 별첨 3) 원문 기준이다.

### 2.1 C-2 지갑/키관리

| 요건 | 요건 내용 | 상세 내용 | 평가 방법 |
|---|---|---|---|
| C-2-1 | 지갑·키 관리 정책을 수립하고 운영할 것 | 생성·폐기·교체 절차의 수립과 운영, 키 분실·도난 대응 체계 마련 | 체크리스트 + 증빙서류(문서번호 13 키관리 정책 설명서) |
| C-2-2 | 키는 계좌(지갑) 관리 주체의 책임 아래 안전하게 보관할 것 | 서명키의 안전한 보관과 사용. 타 기관에 위탁 보관하면 위탁기관이 임의로 서명하지 못하게 통제 장치를 두어 서명의 원본성을 보장 | 체크리스트 |

두 요건 모두 금융보안원이 별도로 제시할 예정인 안내서 준수를 권고한다. 가이드라인은 HSM·MPC 같은 특정 기술을 지정하지 않는다.

| B-4-1 | 보안사고·치명적 오류 시 마스터키 기능 등 권한 통제 방안, 시나리오 기반 장애 대응 프로토콜 | 비상 통제 키와 전체 정지, 대응 절차 (FR-5.5) |

## 3. 기능 요구사항

필수 요구사항은 FR-1~FR-6이다. 이 여섯 개가 동작하면 "기안 → 승인 → HSM 서명 → 원장 제출 → 이벤트 수신 → 감사 검증"이 한 번에 시연된다.

### FR-1 서명 서버 (P0)

- FR-1.1 업무 서버는 개인키와 니모닉을 보유하지 않고, 서명은 서명 서버 API로만 요청한다.
- FR-1.2 서명 서버는 PKCS#11로 HSM에 접근하며, 개인키는 평문으로 HSM 밖에 나오지 않는다. 운영 키는 추출 불가로 만들고, 백업 대상 키만 래핑된 형태로 내보낼 수 있다(D-3).
- FR-1.3 업무 서버와 서명 서버 사이는 상호 TLS로 인증한다.
- FR-1.4 서명 요청은 원문 트랜잭션을 포함하고, 서명 서버가 내용을 해석해 정책을 검사한다(해시만 받는 블라인드 서명 금지).
- FR-1.5 EVM 서명은 HSM이 돌려준 (r, s)를 low-s로 정규화하고 복구 식별자(v)를 계산해 완성한다.

### FR-2 키 금고와 원장·기관별 분리 (P0)

- FR-2.1 원장과 기관(계좌관리기관)마다 HSM 토큰과 접속 자격증명을 분리하고, 다른 기관의 키로는 서명할 수 없게 한다(C-2-2 서명 원본성).
- FR-2.2 키는 용도(발행, 계좌대체, 컨트랙트 관리, 비상 통제, 감사)별로 나누고, 용도 밖의 서명 요청은 거부한다.
- FR-2.3 키 메타데이터(식별자, 원장, 기관, 용도, 상태, 생성·교체·폐기 일시)를 레지스트리로 관리한다.

### FR-3 승인 워크플로우와 정책 (P0)

- FR-3.1 기안자와 승인자를 분리하고, 본인이 기안한 건은 승인할 수 없다. 승인은 승인자 개인 키의 전자서명으로 남기고, 서명 서버가 그 서명을 직접 검증한다(D-2).
- FR-3.2 정책은 수량 한도, 수신 계좌 화이트리스트, 호출 가능한 컨트랙트 함수, 필요한 승인자 수(M-of-N)로 정의한다.
- FR-3.3 요청 상태는 기안 → 승인 대기 → 승인 → 서명 → 제출 → 확정, 또는 반려·만료·실패로 전이한다.
- FR-3.4 키 생성·교체·폐기·복구와 정책 변경도 같은 승인 절차를 거친다.
- FR-3.5 반복·고액 요청은 알람을 내고, 보안관리자가 특정 키나 원장의 서명을 즉시 동결할 수 있다.

### FR-4 감사로그 (P0)

- FR-4.1 서명 요청, 승인·반려, 서명 결과, 키 작업, 정책 변경, 동결을 추가 전용으로 기록한다.
- FR-4.2 각 기록은 직전 기록의 해시를 포함해 체인을 이루고, 검증 명령으로 위변조 여부를 확인한다.
- FR-4.3 체인의 최신 해시를 주기적으로 HSM 키로 서명해 별도 위치에 보관한다.

### FR-5 키 생애주기 (P0)

- FR-5.1 생성: HSM 안에서 키 쌍을 만들고, 주소와 공개키를 레지스트리에 등록한다.
- FR-5.2 교체: 새 키를 만들고 온체인 권한을 새 주소로 옮긴 뒤 이전 키를 서명 불가 상태로 바꾼다.
- FR-5.3 폐기: HSM에서 키를 삭제하고 폐기 증적을 감사로그에 남긴다.
- FR-5.4 백업·복구: 백업 대상 키(컨트랙트 관리, 비상 통제)는 래핑 키로 암호화해 내보내고, 래핑 키는 분할 보관하며, 빈 HSM에 복구하는 리허설을 수행한다. 운영 키(발행, 계좌대체)는 백업하지 않고 분실 시 교체로 복구한다(D-3).
- FR-5.5 분실·도난 대응: 해당 키 동결, 온체인 권한 회수, 비상 통제 키로 종목 유통 정지, 신규 키 투입 순서를 절차와 스크립트로 제공한다.

### FR-6 분산원장 연계 계층 (P0)

- FR-6.1 원장 어댑터 인터페이스(트랜잭션 생성, 제출, 영수증 조회, 이벤트 구독)를 정의하고 Besu 구현을 제공한다.
- FR-6.2 토큰증권 컨트랙트는 종목마다 하나씩 배포하고, 발행, 계좌대체, 말소, 계좌 처분제한, 종목별 유통 정지를 역할 기반 권한으로 제공한다(D-3-1, D-3-2).
- FR-6.3 제출은 멱등 키와 nonce 관리로 중복 제출을 막고, 실패 시 재시도 규칙을 둔다.
- FR-6.4 이벤트는 블록 커서로 수신하고, 확정된 이벤트만 전자등록정보로 추출해 보존한다.

### FR-7 연계장부와 대사 (P1)

- FR-7.1 모의 계좌·잔고 원장을 두고, 온체인 주소와 계좌의 대응을 연계장부에서 관리한다.
- FR-7.2 온체인 잔고·총발행량과 원장 잔고를 주기적으로 대사하고 불일치를 보고한다.

### FR-8 확장 (P2)

- FR-8.1 같은 서명 인터페이스 뒤에 임계값 서명(TSS) 기반 MPC 서명기를 추가한다.
- FR-8.2 Hyperledger Fabric 어댑터를 추가하고, 신원 인증서의 개인키를 HSM에 둔다.

## 4. 비기능 요구사항

- NFR-1 키 비노출: 개인키, HSM PIN, 래핑 키는 로그·응답·저장소·환경 파일 어디에도 평문으로 남지 않는다.
- NFR-2 최소 권한: 각 서버의 DB 계정은 감사로그 테이블을 수정·삭제할 수 없다.
- NFR-3 정합성: 서명 요청은 멱등하고, 같은 요청이 두 번 서명·제출되지 않는다.
- NFR-4 장애 대응: 서명 서버나 HSM이 죽은 상태에서 요청은 대기로 남고, 복구 후 이어서 처리된다.
- NFR-5 검증 가능성: 단위 테스트와 통합 테스트로 정책 위반, 자기 승인, 감사로그 변조, 폐기된 키 사용을 거부하는지 확인한다.
- NFR-6 재현성: 명령 한 줄로 로컬 전체 환경이 기동되고, 시연 스크립트가 전체 흐름을 실행한다.

## 6. 결정사항 (Decision Log)

| 번호 | 결정 | 이유 |
|---|---|---|
| D-1 | 언어는 Go. 저장소는 `da-infra/sto-key-management-signing-mvp` | PKCS#11 메커니즘 직접 호출, Besu 트랜잭션 라이브러리, 공고의 언어 요건 |
| D-2 | 승인은 승인자 개인 키(Ed25519) 서명으로 남기고 서명 서버가 직접 검증한다 | 업무 서버가 침해돼도 승인 없이 서명받을 수 없게 한다(C-2-2 임의 서명 방지) |
| D-3 | 키를 두 부류로 나눈다. 운영 키(발행·계좌대체)는 추출 불가·백업 없음·분실 시 교체. 루트 키(컨트랙트 관리·비상 통제)는 래핑 백업 | PKCS#11에서 추출 불가 속성과 래핑 내보내기는 양립하지 않는다. 온체인 권한을 재부여할 수 있는 키는 백업보다 교체가 안전하다 |
| D-4 | SoftHSM2는 네트워크 서비스가 아니라 라이브러리이므로 서명 서버 컨테이너 안에 두고, 토큰 저장소는 서명 서버만 마운트한다 | 키에 닿는 경로를 하나로 제한 |
| D-5 | 동결은 보안관리자 1인의 서명으로 즉시, 해제는 M-of-N 승인 | 사고 시 차단은 빨라야 하고 복구는 신중해야 한다 |
| D-6 | 한 요청(request_id)은 서명을 한 번만 받는다. 제출 실패 시 요청을 실패로 닫고 새 요청을 만든다 | 이중 서명·이중 제출 방지(NFR-3)를 단순하게 보장 |
| D-7 | 고객 계좌는 온체인 주소로 식별하되 계좌별 개인키는 두지 않고, 계좌관리기관의 운영 키가 계좌대체를 실행한다 | 기재 권한은 작성 책임이 있는 참여자에게 있다(B-2-2). KSD 표준개발요건은 확인하지 못했으므로 MVP 단순화로 명시 |
| D-8 | 시연용 기관은 둘(기관 A, 기관 B)과 플랫폼 운영 주체 하나 | 기관별 키 분리와 타 기관 키 사용 거부를 보여주기 위함 |
| D-9 | 관리 화면은 읽기 전용 웹 한 장, 기안·승인·키 작업은 CLI | 승인 서명을 브라우저에서 다루지 않아 범위를 줄인다 |
| D-10 | 트랜잭션 유형은 EIP-1559(type 2)로 하고 `maxFeePerGas = maxPriorityFeePerGas = 0`으로 서명한다. 가스비 0은 Besu 공식 절차대로 genesis `zeroBaseFee: true`, `baseFeePerGas: 0`, `gasLimit: 0x1fffffffffffff`, `contractSizeLimit` 최대, 모든 노드 `min-gas-price=0`, `tx-pool-enable-balance-check=false`로 구성한다. 마일스톤은 `pragueTime: 0`, Besu 26.11.2 | T0.2 실측(`scripts/check-besu.sh`)에서 잔액 0 계정의 레거시(gasPrice 0)와 type 2(수수료 0)가 모두 확정됨. type 2가 현행 기본 유형이고 v 대신 yParity만 계산하면 된다. 서명 서버는 수수료 필드가 0인지 검사한다 |
| D-11 | HSM은 SoftHSM2 2.6.1(Debian trixie 패키지)을 쓴다. 서명은 secp256k1 + `CKM_ECDSA`, 루트 키 백업은 `CKM_AES_KEY_WRAP_PAD`(AES-256 래핑 키)로 `C_WrapKey`/`C_UnwrapKey` 한다 | T0.3·T0.4 실측에서 키 생성·서명·트랜잭션 확정, EC 개인키 래핑·빈 토큰 복원·주소 일치를 확인했다(`docs/증빙/실측_HSM_서명.md`, `실측_HSM_래핑.md`). 대체 방식(토큰 저장소 암호화 사본)은 필요 없다 |
| D-12 | 감사 체인 추가는 스키마마다 한 행짜리 `audit_head`를 `SELECT … FOR UPDATE`로 잠가 직렬화한다. 서버 계정은 `audit_head`에 SELECT·UPDATE만, 검증은 `audit_log`만 쓴다 | 서버 계정은 추가 전용 테이블에 잠금 읽기를 할 수 없다(M0 실측, MySQL 오류 1142) |
| D-13 | 정책의 수량·수신 계좌 인자 위치는 함수별 인자 역할 표로 정하고, 표에 없는 함수는 정책이 한도·화이트리스트를 요구하면 거부한다. 범위당 ACTIVE 정책은 하나 | 설계서 7.2 가 인자 위치를 정하지 않았다. 알 수 없으면 거부(fail closed) |
| D-14 | 승인 항목 중 하나라도 잘못되면(중복·미등록·비활성·서명 불일치·자기 승인·다른 기관·그룹 밖·반려) 나머지가 M건이어도 요청 전체를 거부한다 | 위조 승인이 섞인 요청은 공격 신호다 |
| D-15 | 동결 해제의 보안관리자 그룹과 필요 서명 수(M=2)는 signerd 설정 `freeze`에 둔다. 동결·해제 메시지는 도메인 구분 + ID 1회 사용 + 요청 시각 ±5분 | 설계서 7.3 이 M 과 그룹의 출처를 정하지 않았다 |
| D-16 | api 감사 체인 체크포인트는 업무 서버가 알려 온 머리를 서명 서버가 AUDIT 키로 증명한다(서명 서버 → 업무 서버 연결 없음, 머리 역행 거부) | 서명 서버는 api 스키마에 접근하지 않고, 키 영역에서 밖으로 나가는 연결을 만들지 않는다 |

미확정

- M6(기존 결제 MVP 연동)을 포함할지: 사용자 확인 전까지 착수하지 않는다.
- 금융보안원 안내서: 공개 여부를 확인하고, 공개되면 FR-1·FR-5와 키관리 정책 설명서를 보정한다.
- 정책·승인자 변경(`POST /v1/policy-changes`, FR-3.4): 작업지시서에 해당 작업이 없어 M2 에서 구현하지 않았다. 지금은 부트스트랩으로만 정책·화이트리스트를 넣을 수 있다. M4 의 계좌 등록에서 화이트리스트를 바꿔야 하므로 작업 추가가 필요하다.

## 7. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| SoftHSM2의 secp256k1 지원 여부 | 안 되면 M1 구조를 바꿔야 함 | 해소(11-27, T0.3): 키 생성·`CKM_ECDSA` 서명·Besu 확정 확인. 단, s가 정규화되지 않아 low-s 정규화가 필수(D-11) |

| 소프트웨어 HSM의 한계 | 실물 HSM의 물리 보호·인증을 증명하지 못함 | 인터페이스가 PKCS#11 표준이라 교체 가능함을 설계서에 명시 |
| 범위 과다 | 필수 범위가 미완성으로 남음 | M3까지를 우선 완성하고 P1·P2는 이후에 착수 |
| MPC 라이브러리 학습 비용 | M5 일정 불확실 | 선택 범위로 분리, 미구현 시 설계 문서로 대체 |
| 기안자 미인증 | 승인자가 다른 담당자 ID 로 기안한 뒤 자기 요청을 승인할 수 있다(자기 승인 검사는 ID 비교) | MVP 는 기안자를 업무 서버가 등록 여부만 확인한다. 보완안: 기안도 기안자 키 서명을 붙이고 서명 서버가 6단계에서 확인 |
