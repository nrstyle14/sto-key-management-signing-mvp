## 공통 사항

- 명령 실행 주체: `bin/stoctl`(관리 CLI)이 mTLS 클라이언트 인증서(CN `stoctl`)로 서명 서버(`https://127.0.0.1:8443`)와 업무 서버(`https://127.0.0.1:9443`)를 호출한다.
- 승인 서명: 승인자·보안관리자마다 암호로 보호한 Ed25519 키 파일(`deploy/approvers/<ID>.json`)이 있다. 명령은 `--approver <ID>`(키 작업·정책 변경) 또는 `--key <파일> --password-file <파일>`(업무 승인·동결)로 서명한다. 시연은 암호 파일을 `deploy/secrets/approver_<ID>_password`에서 읽는다(운영에서는 승인자가 직접 입력, 11절).
- 승인 수 기호: "업무 승인 2" = 같은 기관 승인자 그룹의 서로 다른 승인자 2명(기안자 제외). "보안관리자 2" = 그룹 `platform-security-admins`의 서로 다른 활성 보안관리자 2명. "보안관리자 1" = 1명.
- 감사 기록: 서명 서버 체인(`signer`)과 업무 서버 체인(`api`) 두 개다. 표의 `signer:KEY_GENERATED`는 서명 서버 체인의 action 이다. 요청·키·주소별 기록은 `stoctl audit trail <ID>`로 본다.

## 1. 지갑·키 분류

키는 `(원장, 기관, 용도)` 범위에 속하고, 범위마다 ACTIVE 키는 하나 이하다. HSM 토큰은 `(원장, 기관)` 단위로 나뉘고 토큰마다 PIN 이 다르다(FR-2.1, C-2-2).

| 부류 | 용도 | 보관 토큰(시연) | 하는 일 | 추출 | 백업 | 분실 시 |
|---|---|---|---|---|---|---|
| 운영 키 | ISSUE | `besu-local.inst-a` | 발행·말소(`issue`, `redeem`) | 불가 | 없음 | 교체(5절) |
| 운영 키 | TRANSFER | `besu-local.inst-a`, `besu-local.inst-b` | 계좌대체·계좌 등록·처분제한 | 불가 | 없음 | 교체(5절) |
| 루트 키 | CONTRACT_ADMIN | `besu-local.platform` | 종목 배포, 역할 부여·회수, 기관 대응 | 래핑으로만 | 래핑 백업 | 복구(7절) |
| 루트 키 | EMERGENCY | `besu-local.platform` | 유통 정지·재개, 전체 정지 | 래핑으로만 | 래핑 백업 | 복구(7절) |
| 감사 키 | AUDIT | `audit` | 감사 체크포인트 서명(트랜잭션 서명 불가) | 불가 | 없음 | 새 키로 교체(11절: 시험하지 않음) |

- 고객 계좌(지갑)는 연계장부 계좌마다 무작위 20바이트 주소이고 개인키가 없다(D-7). 계좌의 이동은 계좌관리기관의 TRANSFER 키가 한다. 권리자 이름·계좌번호는 연계장부(`api.accounts`)에만 있고 원장에는 주소와 기관 ID 만 간다(E-2-1).
- 승인자 키(Ed25519)는 HSM 밖의 사람 키다. 트랜잭션에 서명하지 않고 요청(intent)에 대한 승인만 서명한다.
- 키 상태: `PENDING → ACTIVE → RETIRED → DESTROYED`, `PENDING → RETIRED`(교체 취소). 즉시 동결은 상태가 아니라 동결 기록으로 한다(4·8절).

확인: `bin/stoctl key list`(키 ID, 토큰, 기관, 용도, 상태, 주소).

## 2. 생성

| 절차 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 토큰 초기화와 초기 키(설치 1회) | `make up`이 실행하는 `scripts/init-signer.sh`(`signerd init-tokens` → `signerd init --bootstrap`) | 설치 절차(부트스트랩 파일은 두 번째 실행이 거부된다) | `signer:BOOTSTRAP`(토큰·키·승인자·정책 목록) |
| 키 생성 | `bin/stoctl key generate --institution inst-b --purpose TRANSFER --rotated-from key-inst-b-transfer-1 --reason "교체 준비" --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:KEY_GENERATED`(키, 토큰, 용도, 부류, 주소, 상태, 승인자, 사유) / 거부 `signer:KEYOP_REJECTED` |
| 종목 배포(종목 컨트랙트 생성) | `scripts/bootstrap-security.sh <종목코드> <종목명>` | 종목 배포·역할 부여 요청마다 기안 sec-01 + 보안관리자 2 | `api:REQUEST_*`, `signer:SIGN_TX`, `api:SECURITY_REGISTERED` |

- 키는 HSM 안에서 만들어진다(`CKM_EC_KEY_PAIR_GEN`, secp256k1). 운영 키는 `CKA_SENSITIVE=true`, `CKA_EXTRACTABLE=false`다. 개인키 값은 어떤 경로로도 HSM 밖에 나오지 않는다(`CKR_ATTRIBUTE_SENSITIVE`, T1.2 통합 시험).
- 같은 범위에 ACTIVE 키가 없으면 새 키는 ACTIVE 로, 있으면 PENDING 으로 등록된다. PENDING 키는 `--rotated-from`으로 교체 대상을 지정해 만든 경우에만 이전 키 퇴역(`key retire --successor`)과 함께 ACTIVE 가 된다(5절). 교체 대상 없이 만든 PENDING 키는 활성화할 수 없다. 교체를 그만두거나 그런 키를 정리하려면 `key retire --key <새 키>`로 퇴역시킨다(교체 취소).
- 레지스트리에는 공개키와 주소만 저장된다. 서명 서버는 기동할 때 레지스트리의 ACTIVE·PENDING 키가 HSM 에 있는지 대조하고, 없으면 뜨지 않는다.

## 3. 보관

- HSM: SoftHSM2(PKCS#11). 토큰 디렉터리는 서명 서버 컨테이너 전용 볼륨에 있고, 서명 서버만 HSM 라이브러리에 접근한다. 업무 서버(`cmd/apid`)는 `internal/hsm`을 import 할 수 없다(`make lint`의 `scripts/check-imports.sh`).
- 기관 분리: `(원장, 기관)`마다 토큰과 PIN 이 따로다. 서명 서버는 요청의 `(원장, 기관, 용도)`로만 키를 고르므로 다른 기관 키로 서명할 수 없다(5.3 의 4단계). 컨트랙트도 키 주소의 기관과 계좌 기관이 같아야 계좌대체·등록을 받는다(D-17).
- PIN·DB 비밀번호: Docker secret 파일(`deploy/secrets/`, 커밋 금지)로 서명 서버에만 전달하고 환경 변수·로그에 남기지 않는다.
- 위탁기관의 임의 서명 방지(C-2-2): 플랫폼(서명 서버 운영자)도 기관 승인자의 Ed25519 승인 2건 없이는 기관 키로 서명할 수 없다. 승인자 명부와 정책은 서명 서버 DB 에 있고, 업무 서버는 조회만 한다.
- 서명 서버 호출: mTLS 클라이언트 인증서 CN 허용 목록. 트랜잭션 서명 API(`/v1/sign/tx`)는 업무 서버(CN `apid`)만, 키 작업·동결·정책 변경은 `stoctl`만 부를 수 있다.
- 서명 서버는 원장 노드에 접속하지 않는다(`make lint`가 원장 RPC 클라이언트 의존을 막는다).

## 4. 사용(승인과 서명 통제)

### 4.1 업무 요청 흐름

| 단계 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 기안 | `bin/stoctl request draft --institution inst-a --purpose ISSUE --contract <종목> --function "issue(address,uint256)" --args "<주소>,100" --drafter apr-a-01` | 기안자(같은 기관 담당자) | `api:REQUEST_SUBMITTED`(intent 해시, 정책 ID) |
| 승인 | `bin/stoctl request approve <요청> --key deploy/approvers/apr-a-02.json --password-file deploy/secrets/approver_apr-a-02_password` (apr-a-03 도) | 업무 승인 2 | `api:APPROVAL_ADDED` |
| 반려 | `bin/stoctl request reject <요청> --key … --password-file …` | 승인자 1(반려 1건이면 REJECTED) | `api:APPROVAL_ADDED`(decision REJECT) |
| 서명·제출·확정 | 업무 서버 작업자가 자동 처리. `bin/stoctl request wait <요청>` | - | `api:REQUEST_SIGNED`, `signer:SIGN_TX`, `api:REQUEST_LEDGER_SUBMITTED`, `api:REQUEST_CONFIRMED` / 거부 `signer:SIGN_REJECTED`, `api:REQUEST_FAILED` |

- 승인 화면: `stoctl request approve`는 intent(원장, 기관, 키 용도, 컨트랙트, 함수, 인자, 기안자, 만료)를 보여 주고 intent 해시를 로컬에서 다시 계산한 뒤 서명한다.

### 4.2 서명 서버의 검사(설계서 5.3)

서명 서버는 아래를 모두 통과해야만 서명한다. 거부는 사유 코드와 함께 `signer:SIGN_REJECTED`로 남고, 이 단계를 건너뛰는 옵션은 없다.

1. 호출자 인증서(`SIGN_CALLER_NOT_ALLOWED`)
2. 요청 ID 당 서명 1회(`SIGN_REQUEST_CONFLICT`)
3. intent 형식·만료·해시(`INTENT_*`)
4. 범위의 ACTIVE 키, 동결 여부, 업무 서버가 기대한 키 주소(`KEY_NOT_AVAILABLE`, `KEY_FROZEN`, `KEY_ADDRESS_MISMATCH`)
5. 정책: 함수 허용, 수량 한도, 수신 화이트리스트, 가스 상한(`POLICY_*`)
6. 승인: 서로 다른 유효 승인자 M명, 그룹·기관 일치, 기안자 제외(`APPROVAL_*`)
7. 미서명 tx 해석: chainId, `to`, value 0, calldata 가 intent 와 같음, 배포 바이트코드 해시(`TX_*`)
8. HSM 서명 → low-s → 공개키 복구로 주소 확인
9. 서명 기록과 감사 기록을 한 트랜잭션에 저장

### 4.3 정책과 화이트리스트

- 정책은 `(원장, 기관, 용도)`마다 하나다(시연 정책: `bin/stoctl policy list`). 발행·대체 정책의 수량 한도는 100000, 승인 2, 가스 상한 500000 이다.
- 새 연계장부 계좌가 발행·대체를 받으려면 그 주소를 화이트리스트에 넣어야 한다(D-22).

| 절차 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 연계장부 계좌 등록 | `bin/stoctl account register --institution inst-a --holder "홍길동" --security <종목코드> --drafter apr-a-01` 뒤 등록 요청을 업무 승인 2 | 업무 승인 2 | `api:ACCOUNT_CREATED`(이름 제외), `api:REQUEST_*`, `signer:SIGN_TX` |
| 화이트리스트 추가 | `bin/stoctl policy whitelist-add --account <계좌번호> --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:POLICY_WHITELIST_ADDED` / 거부 `signer:POLICY_CHANGE_REJECTED` |

### 4.4 이상 징후 알람

고액(정책 한도의 80% 이상), 같은 키 반복 서명(10분 5건), 같은 기안자 거부 반복(10분 3건), 대사 불일치. 알람은 기록만 하고 자동 동결하지 않는다. 조회: 읽기 전용 웹 `http://127.0.0.1:9080/`.

## 5. 교체

정기 교체나 키 노출 의심 시 쓴다. 운영 키는 백업이 없으므로 분실해도 교체로 대응한다.

| 절차 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 교체(한 번에) | `bin/stoctl key rotate --institution inst-a --purpose ISSUE --drafter sec-01 --approver sec-02 --approver sec-03` | 키 작업 보안관리자 2, 온체인 단계마다 기안 sec-01 + 보안관리자 2 | 아래 단계별 |
| ① 새 키 생성 | (rotate 1단계) | 보안관리자 2 | `signer:KEY_GENERATED`(상태 PENDING, target = 이전 키) |
| ② 새 키에 역할 부여·기관 대응 | (rotate 2단계, 종목마다 `grantRole`, `setAgentInstitution`) | 요청마다 보안관리자 2 | `api:REQUEST_*`, `signer:SIGN_TX`(CONTRACT_ADMIN 키) |
| ③ 이전 키 역할 회수·기관 대응 해제 | (rotate 3단계, 종목마다 `revokeRole`) | 요청마다 보안관리자 2 | 위와 같음 |
| ④ 이전 키 퇴역, 새 키 활성화 | (rotate 4단계, 한 트랜잭션) | 보안관리자 2 | `signer:KEY_RETIRED`, `signer:KEY_ACTIVATED` |

- 단계 사이에서 멈추기: `--until generate|grant|revoke`, 이어 가기: `--resume <새 키 ID>@<마친 단계>`.
- 교체 중 이전 키 주소로 준비된 요청은 서명 서버 4단계 `KEY_ADDRESS_MISMATCH`로 거부된다. 역할 회수 뒤 이전 키로 서명된 tx 는 컨트랙트가 거부한다(`LEDGER_REVERTED`).
- 반드시 모든 종목을 교체한다. `--security`로 종목을 고르면 빠진 종목에는 이전 키 역할이 남는다(11절).
- 검증: `test/rotate_e2e_test.go`(`make it`), 시연 `make demo` ③.

## 6. 폐기

| 절차 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 퇴역(교체 없이) | `bin/stoctl key retire --key <키> --reason "사용 종료" --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:KEY_RETIRED` |
| 폐기 | `bin/stoctl key destroy --key <키> --reason "폐기" --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:KEY_DESTROYED`(토큰, 주소, 삭제 전·후 HSM 객체 수 `objects_before`·`objects_after`) |

- RETIRED 키만 폐기할 수 있다. 서명 서버는 `C_DestroyObject` 뒤 같은 라벨의 객체 수를 다시 세어 0 일 때만 DESTROYED 로 바꾼다. 응답의 `objects_remaining`이 0 이어야 한다.
- 폐기 증적 확인: `bin/stoctl audit trail <키> --require "signer:KEY_RETIRED,signer:KEY_DESTROYED"`.
- 폐기는 되돌릴 수 없다. 루트 키를 폐기하기 전에 백업이 필요 없는지 확인한다.

## 7. 백업·복구

루트 키(CONTRACT_ADMIN, EMERGENCY)만 백업한다(D-3). 래핑 키는 Shamir 2-of-3 으로 나눠 보관자 3명이 조각을 하나씩 갖는다.

| 절차 | 명령 | 승인 | 감사 기록 |
|---|---|---|---|
| 래핑 키 의식 | `bin/stoctl key ceremony --institution platform --threshold 2 --custodian custodian-1 --custodian custodian-2 --custodian custodian-3 --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:KEY_WRAP_INSTALLED`(래핑 키 ID, 토큰, 약속값 SHA-256, 승인자. 키 값 없음) |
| 루트 키 백업 | `bin/stoctl key backup --key key-platform-contract-admin-1 --wrap-key <래핑 키 ID> --approver sec-02 --approver sec-03` | 보안관리자 2 | `signer:KEY_BACKED_UP`(암호문 SHA-256) |
| 복원 | `bin/stoctl key restore --backup <백업 파일> --share <조각1> --share <조각2> --approver sec-02 --approver sec-03` (운영 서명 서버에서는 재현되지 않음: 토큰을 잃으면 서명 서버가 기동하지 않는다, 11절. 같은 래핑·복원은 리허설로 재현) | 보안관리자 2 + 조각 2개 | `signer:KEY_RESTORED` |
| 복구 리허설 | `scripts/rehearsal-restore.sh` | 의식·백업에 보안관리자 2 | 위 기록 + `docs/증빙/복구리허설_YYYYMMDD.md` |

- 조각 파일은 `deploy/ceremony/<의식>/<보관자>.share`(0600), 백업 파일은 `deploy/backups/`에 생긴다. 둘 다 커밋 금지이며, 운영에서는 보관자별로 분리된 매체로 옮기고 원본을 지운다.
- 복원은 레지스트리에 있고 HSM 객체가 없는 키에만 된다. 복원한 키로 서명해 복구한 주소가 레지스트리 주소와 다르면 복원 객체를 지우고 거부한다(`KEYOP_RESTORE_MISMATCH`).
- 리허설은 운영 토큰을 건드리지 않는다. 서명 서버 이미지의 일회용 컨테이너(네트워크 없음, 빈 토큰)에 조각 2개로 복구하고 주소 일치를 확인하며, 조각 1개로는 실패하는지도 확인한다. 최근 결과: [복구리허설_20261127.md](증빙/복구리허설_20261127.md).

## 8. 분실·도난 대응

`scripts/incident-key-compromise.sh <기관>/<용도>`(기본 `inst-a/TRANSFER`)가 아래 순서를 실행하고 단계별 소요 시간과 감사 머리 seq 를 출력한다.

| 단계 | 하는 일(명령) | 승인 | 감사 기록 |
|---|---|---|---|
| ① 동결 | `bin/stoctl freeze key <키> --reason "탈취 의심" --key deploy/approvers/sec-01.json --password-file deploy/secrets/approver_sec-01_password` (기관 전체는 `freeze institution`, 원장 전체는 `freeze ledger`) | 보안관리자 1 (업무 서버가 죽어 있어도 동작) | `signer:FREEZE` |
| (확인) | 탈취 키로 승인 2건이 붙은 요청을 시도 → 서명 서버 4단계 거부 | - | `signer:SIGN_REJECTED`(KEY_FROZEN), `api:REQUEST_FAILED` |
| ② 역할 회수 | `bin/stoctl security grant-role --contract <종목> --role TRANSFER_AGENT --key <키> --revoke true --drafter sec-01`, `bin/stoctl security set-agent --contract <종목> --key <키> --clear --drafter sec-01` (이전 키가 역할을 가진 모든 종목) | 요청마다 보안관리자 2 | `api:REQUEST_*`, `signer:SIGN_TX` |
| ③ 유통 정지 | 비상 통제 키 `setCirculation(false)` 요청(`bin/stoctl request draft --institution platform --purpose EMERGENCY …`) | 보안관리자 2 | 위와 같음 |
| ④ 새 키 투입 | `bin/stoctl key generate … --rotated-from <키>` → 역할 부여·기관 대응 → `bin/stoctl key retire --key <키> --successor <새 키>` | 보안관리자 2(키 작업), 요청마다 보안관리자 2 | `signer:KEY_GENERATED`, `signer:KEY_RETIRED`, `signer:KEY_ACTIVATED` |
| ⑤ 유통 재개 | `setCirculation(true)` 요청, 새 키로 계좌대체 확인 | 보안관리자 2 | `api:REQUEST_*`, `signer:SIGN_TX` |
| ⑥ 이전 키 폐기 | `bin/stoctl key destroy --key <키> …` | 보안관리자 2 | `signer:KEY_DESTROYED` |

- 동결 해제: `bin/stoctl freeze release <freeze_id> --key <보안관리자1 키> --password-file … --key <보안관리자2 키> --password-file …`(보안관리자 2, `signer:FREEZE_RELEASED`). 동결 목록: `bin/stoctl freeze list`.
- 승인자 키 분실·유출: 승인자 비활성화·교체 명령은 구현하지 않았다(11절). 그 기관 요청을 막으려면 기관 범위 동결(`freeze institution`)을 쓴다.
- 실측(시연 환경, 종목 3개): 동결 0.1초, 전체 약 79초. 결과 표는 스크립트 출력에 있다.

## 9. 감사

| 절차 | 명령 | 승인 | 결과 |
|---|---|---|---|
| 두 체인·체크포인트 검증 | `bin/stoctl audit verify` | - | 체인별 레코드 수, 머리 seq·해시, 체크포인트 수. 어긋나면 첫 seq 와 사유 |
| 체크포인트 생성 | `bin/stoctl audit checkpoint`(주기 실행도 있음) | - | HSM AUDIT 키가 두 체인 머리를 서명해 `signer.audit_checkpoints`와 파일 볼륨에 저장 |
| 요청·키별 기록 | `bin/stoctl audit trail <요청|키|주소> [--require …]` | - | 두 체인의 관련 레코드 |
| 머리 seq | `bin/stoctl audit head` | - | `signer=<seq> api=<seq>` |
| 대사 | `bin/stoctl recon run [--security <종목>]`, `bin/stoctl recon show [run_id]` | - | 계좌 잔고·총발행량·이벤트 재생 비교. 실행마다 `api:RECON_RUN`. 불일치면 알람 `TOTAL_MISMATCH`(같은 종목 24시간에 한 번)와 종료 코드 3 |

- 감사로그는 추가 전용 해시 체인이다. 서버용 DB 계정은 `audit_log`에 INSERT·SELECT 만 가진다(UPDATE·DELETE 거부, `test/dbgrants_test.go`).
- 관리자 권한으로 고친 레코드는 체인 검증이 그 seq 에서 찾는다. 체크포인트 사이 구간을 유효한 체인으로 다시 써도 다음 체크포인트의 머리 해시가 맞지 않아 드러난다(T2.7 시험).
- 감사 payload 는 허용 키 목록만 받는다. 개인키, PIN, 래핑 키, 승인자 개인키, 비밀번호, 권리자 이름이 들어갈 자리가 없다.
- 시연: `make demo` ⑤(검증, 서버 계정 UPDATE 거부, 관리 계정 변조 탐지 — 일회용 복사본에서), ⑥(대사 불일치 탐지).

## 10. 역할과 책임

| 역할 | 시연 주체 | 책임 | 할 수 없는 것 |
|---|---|---|---|
| 기안자 | 기관 담당자(apr-a-01 등) | 업무 요청 기안 | 자기 기안 승인(`APPROVAL_SELF`) |
| 승인자 | 기관 승인자 그룹(inst-a-approvers, inst-b-approvers) | 소속 기관 요청의 intent 확인과 승인·반려 | 다른 기관 요청 승인(`APPROVAL_INSTITUTION_MISMATCH`) |
| 보안관리자 | 플랫폼(sec-01~03, platform-security-admins) | 키 생성·교체·폐기·백업·복원 승인(2명), 화이트리스트 추가 승인(2명), 즉시 동결(1명), 동결 해제(2명), 플랫폼 온체인 요청 기안·승인 | 혼자서 키 작업·동결 해제 |
| 래핑 키 보관자 | custodian-1~3 | Shamir 조각 1개씩 분리 보관, 복구 때 조각 제출 | 혼자서 래핑 키 복원(조각 2개 필요) |
| 서명 서버 운영자 | 플랫폼 | 서명 서버·HSM·PIN 운영, 체크포인트 보관 | 승인 없이 기관 키 서명(5.3 의 6단계) |
| 업무 서버 운영자 | 플랫폼 | 요청 처리, 원장 제출, 연계장부·대사 | HSM 접근, 감사로그 수정 |

한 사람이 여러 역할을 가질 수 있지만 자기 기안을 승인할 수 없고, 키 작업·동결 해제는 서로 다른 보안관리자 2명이 필요하다.

## 11. MVP 의 한계

구현하지 않았거나 시연용으로 단순화한 것이다(설계서 14절, 요구사항 7절 리스크).

- **HSM**: SoftHSM2 는 소프트웨어 구현이라 물리 보호와 인증 등급이 없다. PKCS#11 표준 인터페이스이므로 실물 HSM 으로 바꿀 수 있다. 서명 서버 호스트가 침해되면 토큰 파일과 PIN 이 함께 노출된다(운영은 네트워크 HSM 과 망 분리).
- **승인자 키**: 로컬 파일이다. 시연 자동화를 위해 키 파일 암호도 `deploy/secrets/`에 두었다(운영은 승인자 직접 입력, 보안 토큰 또는 인증서 기반 전자서명).
- **승인자·정책 변경**: 화이트리스트 주소 추가만 구현했다. 화이트리스트 삭제, 정책 본문 변경, 승인자 추가·비활성화·키 교체는 부트스트랩으로만 넣을 수 있다.
- **기안자 인증**: 업무 서버는 기안자가 등록된 담당자인지만 본다. 승인자가 다른 담당자 ID 로 기안한 뒤 자기 요청을 승인할 수 있다(보완안: 기안자 키 서명).
- **토큰 분실 시 복원 경로**: 서명 서버는 ACTIVE 키의 HSM 객체가 없으면 기동하지 않으므로, 실제로 토큰을 잃으면 `stoctl key restore`를 부를 수 없다. 래핑·복원 자체는 리허설(일회용 빈 토큰)로 실제 SoftHSM2 에서 확인했고, 운영 서명 서버의 RESTORE 는 시험용 HSM 대역으로만 시험했다.
- **래핑 키 전달**: 래핑 키 값이 의식 때 stoctl 에서 서명 서버로 mTLS 위에서 한 번 전달되고, 메모리에서 확실히 지울 수 없다. 조각 파일은 보관자 공개키로 암호화하지 않는다.
- **부분 교체**: `key rotate --security`로 일부 종목만 교체하면 빠진 종목에 이전 키 역할이 남는다. 운영은 전체 종목을 교체한다.
- **감사 체크포인트 파일**: `stoctl audit verify`는 DB 의 체크포인트만 확인한다. DB 관리자가 `audit_log`와 `audit_checkpoints`를 함께 고치면 체크포인트 파일과 수동으로 대조해야 드러난다. 마지막 체크포인트 이후 구간의 재작성은 다음 체크포인트 전까지 알 수 없다.
- **감사 키 교체**: `key generate`·`key retire --successor`로 AUDIT 키도 교체할 수 있게 되어 있지만 시험하지 않았다. 이전 체크포인트를 이전 감사 키 공개키로 계속 검증하는지도 확인하지 않았다.
- **읽기 전용 웹**: 인증이 없다. 호스트 쪽은 127.0.0.1 로만 게시하지만 업무 서버와 같은 Docker 네트워크의 컨테이너에서는 닿는다.
- **대사 알람 억제**: 같은 종목의 대사 불일치 알람은 24시간에 한 번이다. 그 안에 다른 불일치가 새로 생기면 알람은 나지 않고 대사 기록과 화면에만 남는다. 연계장부 정정(수량 수정) 명령은 없다.
- **대사 비용**: 대사는 종목마다 모든 연계장부 계좌의 `balanceOf`를 부른다. 기준 블록(이벤트 커서) 시점 조회는 최신 블록 근처에서만 실측했다.
- **시간 초과로 닫은 제출**: 제출 뒤 10분 동안 영수증이 없어 FAILED 로 닫은 tx 가 나중에 확정될 수 있다. 원장 이벤트는 보존되고 대사가 연계장부와의 차이를 보고한다.
- **분산원장**: 로컬 Besu 4노드(QBFT)만 쓴다. Fabric 어댑터와 MPC 서명기(M5)는 구현하지 않았다.
